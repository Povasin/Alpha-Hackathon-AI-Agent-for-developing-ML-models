# AI-агент для разработки ML-моделей

## 1. Назначение и краткое описание

- **Секция:** AI-агент для разработки ML-моделей.
- **Тур:** Онлайн тур.
- **Назначение:** самостоятельное техническое описание задачи для ИИ-агента, разрабатывающего решение.
- **Результат разработки:** универсальная агентная система, упакованная в ZIP-архив с точкой входа `solution.py`.
- **Результат каждого запуска системы:** готовый файл предсказаний для текущей ML-задачи в формате платформы.

Необходимо разработать агента, который получает описание ранее неизвестной задачи и ее данные, самостоятельно проводит исследование, обучает модели и формирует предсказания. Один и тот же код должен работать на разных задачах без ручной настройки под конкретный датасет.

Документ содержит постановку задачи, ограничения, описание публичных данных, исследовательский цикл и формулы оценки. Для понимания задачи другие описательные материалы не требуются. Для реализации и запуска дополнительно нужны технические файлы: `baseline.py`, `requirements.txt` и данные задач. Их назначение и адреса приведены в разделе 12. Параметры, которые нельзя достоверно определить без этих файлов, перечислены в разделе 13.

## 2. Постановка задачи

Создайте AI-агента, который самостоятельно решает задачи машинного обучения: от чтения условия до готового файла с предсказаниями. Для этого:

1. **Анализ задачи.** Научите агента анализировать текстовое описание задачи, изучать структуру входных данных, определять тип ML-задачи и требования к результату.
2. **Автоматизация решения.** Автоматизируйте построение решения, где агент сам выбирает подход, генерирует и запускает код, обучает модель, оценивает качество на собственной валидации и формирует итоговые предсказания.
3. **Цикл AutoResearch.** Добавьте цикл AutoResearch. Агент анализирует результаты экспериментов, формулирует гипотезы для улучшения модели, проверяет их и выбирает лучший вариант решения.
4. **Универсальность.** Обеспечьте универсальность. Один и тот же код должен решать разные задачи, включая классификацию и регрессию и другие задачи машинного обучения, без ручной настройки под конкретный датасет.
5. **Проверка на платформе.** Отправьте агента на платформу. Решение проверяется на двух публичных задачах, а итоговый результат определяется на двух скрытых, которые агент увидит впервые.

## 3. Формат сдачи и контракт запуска

### 3.1. Архив решения

- На платформу загружается ZIP-архив с решением.
- В корне архива должен лежать `solution.py` - единая точка входа для запуска агента.
- Логику можно распределить по нескольким собственным `.py`-модулям в корне архива: `solution.py` импортирует их и вызывает нужный код.
- Размер ZIP-архива не должен превышать **100 МБ**.
- При переносе решения платформа копирует в контейнер **только корневые `.py`-файлы и `requirements.txt`**. Наличие другого файла в ZIP не означает его доступность при запуске.
- Отдельные файлы весов моделей и прочих заранее подготовленных артефактов не копируются. Нельзя рассчитывать и на перенос модулей из вложенных каталогов.
- Платформа запускает решение в Docker-контейнере.
- Переменные окружения, интерфейс запуска и формат вывода зафиксированы в `baseline.py`.
- Решение должно строго соблюдать этот интерфейс, иначе платформа не сможет его проверить.
- Платформа автоматически запускает `solution.py` и передает необходимые параметры, включая путь к описанию задачи. Вручную задавать параметры на платформе не нужно.
- Команда запуска: `python3 solution.py task.md`.
- При подготовке решения необходимо ориентироваться на обработку аргументов в `baseline.py`.
- Весь необходимый код должен находиться в ZIP-архиве. Добавлять сторонние библиотеки, в том числе файлы `.whl`, нельзя.

### 3.2. Лимит отправок

- Не более **3 сабмитов в день на команду**.
- Лимит обновляется ежедневно в **00:00 по МСК**.
- Каждая отправка считается одним сабмитом.
- Не отправляйте решение повторно до отображения score предыдущей отправки: повторная отправка также расходует сабмит.
- Если score равен нулю, он отображается в интерфейсе платформы.

### 3.3. Автономный запуск

- Для каждой задачи агент запускается отдельно.
- Он получает материалы только текущей задачи и формирует ответ для нее.
- Файлы и результаты решения одной задачи в следующую задачу не передаются.
- Внутри запуска агент самостоятельно анализирует данные, организует валидацию на обучающей выборке, генерирует и исполняет код, обучает модели и проверяет гипотезы.
- Метрики для сравнения экспериментов агент рассчитывает сам на собственной валидационной выборке.
- Платформа не оценивает промежуточные предсказания на скрытом тесте и не возвращает агенту обратную связь.
- На одну задачу отводится не более **3 часов**. Агент может завершить работу раньше.
- По истечении 3 часов процесс принудительно останавливается. К этому моменту файл предсказаний уже должен быть сформирован; оценивается уже сформированный файл.
- По уточнению пользователя от 20 октября 2026 года, три часа считаются с момента запуска кода решения (`solution.py`). В общий срок входят подготовка данных, импорты, обращения к LLM, эксперименты, финальное обучение и запись предсказаний.

### 3.4. Рабочий каталог и итоговый файл

- Перед запуском код решения копируется в папку текущей задачи и выполняется из нее.
- `solution.py` и текстовое описание задачи `task.md` находятся в одном каталоге.
- Итоговый файл нужно сохранить под именем `submission.csv` в том же каталоге, где находятся `solution.py` и `task.md`.
- Разрешено создавать файлы и подкаталоги в рабочем каталоге, а также использовать `/tmp` для временных файлов.
- Временные файлы и промежуточные модели не заменяют итоговый `submission.csv`.

Схема размещения основных файлов при запуске:

```text
<каталог задачи>/
  solution.py
  task.md
  submission.csv    # результат работы агента
```

### 3.5. Совместная разработка и GitHub

- Для совместной разработки разрешено использовать GitHub, включая приватные репозитории.
- Ограничение относится к выполнению сабмита на платформе: обращаться к Git и загружать код из репозитория во время запуска нельзя.
- Все необходимые собственные модули решения должны быть включены в корень ZIP-архива как `.py`-файлы заранее.

### 3.6. Проверка решения в Boosters

- После загрузки ZIP платформа проверяет файл, передает решение в Boosters и ставит его в очередь.
- Статус **«Решение находится на проверке»** означает, что решение принято в очередь; это еще не результат проверки.
- После успешной проверки платформа показывает **«Точность вычисления: …»** с полученной оценкой.
- Если отправить решение или завершить проверку не удалось, платформа показывает сообщение об ошибке.
- Не отправляйте новую версию, пока не отобразился результат предыдущей: действует дневной лимит из раздела 3.2.

### 3.7. Ошибки загрузки и отправки

| Сообщение платформы | Что делать |
| --- | --- |
| «Выберите файл решения» | Прикрепить ZIP-архив с решением. |
| «Допустимы только файлы CSV или ZIP» | Для трека AutoML загрузить ZIP, подготовленный по требованиям раздела 3.1. |
| «Файл пустой. Загрузите файл с решением» | Проверить содержимое архива и загрузить его повторно. |
| «Размер файла не должен превышать 128 мегабайт» или «Файл решения слишком большой» | Уменьшить архив. Для AutoML действует лимит **100 МБ**, даже если загрузчик показывает больший технический порог. |
| «В файле решения ошибки: …» | Исправить ошибки, перечисленные в сообщении. |
| «Не удалось загрузить файл», «Не удалось получить публичную ссылку на файл решения» или «Не удалось отправить решение» | Повторить загрузку. Если ошибка повторяется, обратиться к организаторам. |
| «Задание ещё готовится», «Команда ещё подключается к системе заданий» или «Ваш профиль ещё синхронизируется» | Подождать и отправить файл еще раз. |

| «Команда не допущена к этому туру», «Команда дисквалифицирована» или «Вы не состоите в этой команде» | Если сообщение кажется ошибочным, обратиться к организаторам для проверки статуса команды или участника. |

### 3.8. Ошибки во время проверки

| Сообщение платформы | Что означает и что проверить |
| --- | --- |
| «Ошибка формата данных» | Проверить соответствие файлов формату задачи и контракту `baseline.py`. |
| «Превышено время обработки решения» | Решение не уложилось в лимит времени; проверить длительность полного запуска, включая обращения к модели. |
| «Не хватает данных в решении» | Проверить, что скрипт сформировал все требуемые результаты. |
| «Не хватает данных в решении: отсутствует файл …» | Проверить, что указанный файл создается и сохраняется в требуемом каталоге. `submission.csv` должен находиться рядом с `task.md`. |
| «Ошибка скоринга сабмита. Попробуйте позже» | Повторить попытку позже; если ошибка сохраняется, обратиться к организаторам. |

При обращении к организаторам приложить **текст ошибки или скриншот и время отправки решения**. Подробные технические логи доступны только администраторам и могут не отображаться в интерфейсе участника.

### 4.1. Зависимости всего решения

`requirements.txt` - единый фиксированный список зависимостей для всех частей решения:

- кода самого агента;
- инструментов, которые вызывает агент;
- кода, который агент генерирует и запускает во время исследования.

Все части выполняются в одном контейнере. Зависимости вне списка недоступны, поэтому генерируемый код также должен использовать только предоставленные пакеты. Добавление библиотеки в ZIP, включая `.whl`, не допускается.

Если нужна дополнительная библиотека или модель, можно запросить ее в чате хакатона. Дополнительные модели могут быть включены в список зависимостей после согласования с экспертами. До согласования и включения в доступный список рассчитывать на такую зависимость нельзя.

### 4.2. Диск и бюджет разработки

- Отдельной дисковой квоты на запуск нет. Ориентир свободного места - **30-35 ГБ**, а не гарантированный персональный объем для каждого запуска.
- Для промежуточных файлов разрешены рабочий каталог, его подкаталоги и `/tmp`.
- **600 рублей - суточное ограничение только на разработку решения. Запуски на платформе не расходуют этот лимит.** Из этого не следует неограниченный доступ к LLM при проверке: параметры такого доступа определяются платформой.
- Дополнительно указано: «Отдельного лимита по количеству нет». Объект этого ограничения не уточнен; эту формулировку нельзя использовать для отмены лимита сабмитов или других явно установленных ограничений. См. раздел 13.

### 4.4. Отсутствие MCP и выполнение инструментов скриптом сабмита

- Пакет `mcp` не включен в `requirement.txt` и не установлен в контейнере платформы.
- При этом предоставленный `baseline.py` импортирует `ClientSession`, `StdioServerParameters`, `stdio_client` и `FastMCP` из пакета `mcp` на уровне модуля.
- Поэтому неизмененный baseline в этом контейнере завершится с `ModuleNotFoundError` при импорте `mcp`, до начала работы агента. Сам факт наличия импорта в baseline не означает доступность зависимости.
- Решение должно сохранять контракт запуска и вывода платформы, но не должно зависеть от отсутствующего пакета `mcp`. Реализацию инструментов baseline нельзя переносить в `solution.py` без учета этого ограничения.
- Устанавливать `mcp` при выполнении сабмита или добавлять его в ZIP как стороннюю библиотеку нельзя. Использование дополнительной зависимости возможно только после согласования и включения в окружение платформы.

**Инструменты предоставляет и выполняет сам скрипт сабмита:**

1. Скрипт определяет доступные инструменты, их описания и формат аргументов и передает эти сведения модели.
2. Модель выбирает действие и возвращает имя инструмента и аргументы. Модель не выполняет код сама.
3. Скрипт разбирает и проверяет вызов, выполняет соответствующее действие в контейнере с использованием доступных зависимостей, например запускает Python через стандартный `subprocess`.
4. Скрипт получает результат выполнения: вывод, ошибки, код завершения или другую информацию инструмента, и передает его обратно модели.
5. Модель учитывает результат при выборе следующего действия. Цикл продолжается до завершения задачи или достижения ограничений запуска.

```text
Скрипт: описания инструментов -> Модель: выбор действия и аргументы
                                      |
                                      v
Модель: следующий шаг <- Скрипт: результат <- Скрипт: выполнение инструмента
```

Для такой схемы MCP-сервер и пакет `mcp` не обязательны: исполнение инструментов организуется непосредственно в коде сабмита. Конкретный формат вызовов должен соответствовать возможностям API модели; отсутствие `mcp` в контейнере само по себе не определяет поддержку `tool calling` сервером LLM.

### 4.5. Собственные модели и заранее подготовленные артефакты

Разрешено использование заранее подготовленных командой артефактов, включая веса собственных моделей, обученных офлайн с нуля. Такие модели не подпадают под запрет на сторонние предобученные модели при соблюдении следующих условий:

- Модель самостоятельно обучена командой с нуля и не использует сторонние предобученные модели.
- Решение полностью работает в контейнере без доступа к интернету с доступными зависимостями из `requirements.txt`.
- Соблюдаются остальные правила соревнования, включая ограничение на используемые обучающие данные. Разрешение на собственные артефакты не дает разрешения на внешние данные.
- Все необходимые для работы модели компоненты передаются в поддерживаемом платформой формате.

**Техническое ограничение важнее самого факта добавления артефакта в ZIP:** платформа переносит только корневые `.py`-файлы и `requirements.txt`. Отдельные файлы с весами и другими артефактами в контейнер не копируются. Поэтому простой упаковки таких файлов в архив недостаточно для использования собственной модели.

Разрешение на собственную модель не подтверждает конкретный способ передачи ее весов через поддерживаемые файлы. До выбора такого способа необходимо убедиться, что он совместим с правилами соревнования и механизмом переноса решения. Нельзя предполагать поддержку отдельного файла артефакта.

Это ограничение относится к переносу заранее подготовленных файлов решения. Оно не отменяет возможность создавать файлы, модели и подкаталоги во время выполнения в рабочем каталоге и `/tmp`, а также не меняет предоставление платформой `task.md` и данных текущей задачи.

## 8. Цикл AutoResearch

```text
Гипотеза -> Эксперимент -> Оценка -> Следующая итерация
    ^                                      |
    +--------------------------------------+
```

1. **Гипотеза.** Агент формулирует предположение, которое может улучшить результат. Пример: добавление признака «возраст здания» снизит ошибку прогноза.
2. **Эксперимент.** Агент пишет и запускает код проверки: например, генерирует признак и переобучает модель.
3. **Оценка.** Агент сравнивает результат с предыдущим лучшим по метрике на валидационной выборке.
4. **Следующая итерация.** Если гипотеза подтвердилась, изменение сохраняется. Если нет, агент анализирует причину и выбирает следующее направление.

Число итераций не фиксировано: исследование ограничивается временем на задачу, доступной памятью, вычислительными ресурсами и лимитом LLM. При выборе следующего эксперимента необходимо учитывать время, нужное для финального обучения и формирования предсказаний.

## 9. Публичная и приватная проверка

### 9.1. Public

- Две задачи: регрессия и многоклассовая классификация.
- Платформа рассчитывает метрики по скрытым целевым значениям тестовых выборок.
- Результаты объединяются в `public score`.
- Команды видят результат на публичном лидерборде и могут отправлять новые версии решения в пределах лимита.

### 9.2. Private

- Две новые задачи; их содержание и метрики не раскрываются заранее.
- Платформа выбирает сохраненную последнюю версию решения с лучшим `public score` и повторно запускает ее через `solution.py`.
- Вместо публичных материалов агент получает описания и данные приватных задач через тот же интерфейс из `baseline.py`.
- **Код решения остается неизменным.**
- Платформа рассчитывает метрики и итоговый `private score`.
- Ограничения времени и ресурсов, требования к формату вывода и принцип объединения результатов сохраняются.
- Формулировка о выборе версии не уточняет все правила разрешения равенства результатов; см. раздел 13.

## 10. Метрики и расчет score

### 10.1. Регрессия: RMSE

```text
RMSE = sqrt((1 / n) * sum((y_i - y_hat_i)^2, i = 1..n))
```

- `n` - число объектов тестовой выборки.
- `y_i` - истинное значение.
- `y_hat_i` - предсказание агента.
- Чем меньше RMSE, тем лучше.

### 10.2. Многоклассовая классификация: Macro F1

Для каждого класса:

```text
F1_k = (2 * TP_k) / (2 * TP_k + FP_k + FN_k)
MacroF1 = (1 / K) * sum(F1_k, k = 1..K)
```

- `K` - число классов.
- `TP_k` - число верных положительных предсказаний для класса `k`.
- `FP_k` - число ложных положительных предсказаний для класса `k`.
- `FN_k` - число ложных отрицательных предсказаний для класса `k`.
- Каждый класс имеет одинаковый вес.
- Чем выше Macro F1, тем лучше.
- Точные параметры реализации метрики, включая обработку нулевого знаменателя, нужно сверить с реализацией оценивания платформы.

### 10.3. Перевод публичных метрик в баллы

Метрика каждой задачи нормируется относительно результата бейзлайна на той же тестовой выборке:

```text
S_reg = 100 * max(0, 1 - RMSE / B_RMSE)
S_cls = 100 * max(0, (MacroF1 - B_F1) / (1 - B_F1))
```

- `B_RMSE > 0` - RMSE бейзлайна.
- `B_F1 < 1` - Macro F1 бейзлайна.
- Результат на уровне бейзлайна или хуже дает 0 баллов.
- Идеальный результат дает 100 баллов.
- Численные значения `B_RMSE` и `B_F1` в этом описании не заданы; для численного расчета score нужны результаты бейзлайна на соответствующем тесте.

### 10.4. Публичный score

Обе задачи имеют одинаковый вес:

```text
Score_public = (S_reg + S_cls) / 2
```

Диапазон: от 0 до 100. Чем выше score, тем выше позиция команды в лидерборде.

### 10.5. Приватный score

```text
Score_private = (S_1 + S_2) / 2
```

- `S_1`, `S_2` - баллы по первой и второй приватным задачам.
- Метрики задач могут различаться.
- Балл каждой задачи рассчитывается по формуле, соответствующей ее метрике.
- Нельзя считать, что приватные задачи обязательно используют RMSE и Macro F1: заранее их метрики не раскрыты.

## 11. Цель агентного подхода и качество решения

Исследовательский цикл включает анализ данных, выбор подхода, эксперименты, сравнение результатов и возврат к признакам и валидации. Требуется автоматизировать принятие этих решений, а не ограничиться заранее заданным перебором гиперпараметров.

Агентная система должна удерживать контекст задачи, помнить результаты предыдущих экспериментов, планировать следующие шаги и менять стратегию по результатам проверок. Допускается распределение ролей между несколькими агентами: например, анализ данных, формулировка гипотез и оценка результатов.

LLM может ошибаться при генерации кода и интерпретации результатов. Поэтому выбор улучшений должен опираться на фактическое выполнение кода и метрики собственной валидации. Улучшение оценки должно соответствовать качеству предсказаний, а не эксплуатации ошибок процедуры оценки.

2. **Начало отсчета времени — закрыто.** По уточнению пользователя от 20 октября 2026 года, три часа считаются с момента запуска кода решения. Точка входа архива — `solution.py`. Все этапы выполнения входят в общий срок; готовый `submission.csv` должен существовать до принудительного завершения.
3. **Настройки LLM — частично закрыто.** Обозначение доступной модели — `Qwen3.8-27B`. Локальный `baseline.py` подтверждает переменные `OPENAI_MODEL`, `OPENAI_API_KEY`, `OPENAI_BASE_URL` и использование Chat Completions. Их значения предоставляет платформа. Возможности tool calling, поддерживаемые параметры, лимиты и доступ к API при запрете общего интернета остаются предметом проверки. Инфраструктура развертывания Qwen, скорость генерации в токенах в секунду и размер KV cache не заданы; по уточнению организаторов, эти параметры можно указывать самостоятельно, но их следует считать допущениями, а не подтвержденными характеристиками платформы.
4. **Лимит LLM.** 600 рублей относятся только к суткам разработки; запуск на платформе в этот лимит не входит. Точное число токенов, тарифы и параметры LLM-доступа при проверке не заданы. Нельзя считать 600 рублей бюджетом каждой задачи или трактовать исключение платформы из этого бюджета как отсутствие всех ограничений API.
5. **Схема словаря данных.** Для классификации наличие поля `unit` не подтверждено. Необходимо читать фактические столбцы `data_dictionary.csv`.
6. **Выбор версии для private.** Используется сохраненная последняя версия с лучшим `public score`. Правила разрешения равенства score нужно уточнить у платформы, если это влияет на выбор отправки.
7. **Зависимости — перечень закрыт.** Прочитан корневой `requirement.txt`; список и версии отражены в разделе 4.3. Фактическое имя локального файла отличается от названия `requirements.txt` в материалах платформы. Пакет `mcp` в списке отсутствует и в контейнере не установлен, хотя baseline его импортирует. Собственный скрипт должен предоставлять и выполнять инструменты без обязательной зависимости от `mcp`; см. раздел 4.4. Полная проверка остальных импортов в целевом контейнере отдельно не выполнялась.
8. **Метрики.** Численные значения метрик бейзлайна и точные параметры реализации Macro F1 не заданы в этом описании. Они нужны для полного воспроизведения оценивания.
9. **Приватные задачи.** Типы задач, таргеты и метрики заранее неизвестны. Их нужно определять из материалов текущего запуска. Нельзя жестко закреплять `site_eui`, `attack_cat`, RMSE или Macro F1 для всех задач.
10. **Формулировка о количестве.** Уточнение «Отдельного лимита по количеству нет» не указывает, что именно считается: файлы, обращения или другие объекты. Без уточнения нельзя приписывать ему конкретный смысл. Лимит 3 сабмитов в день сохраняется.
11. **Локальная модель `ZLM`.** Название приведено без расшифровки. Точная модель и ее допустимость для конкретного применения не установлены; это идея для локальных экспериментов, не подтвержденная зависимость платформы.
12. **Собственные модели и перенос артефактов — правило уточнено.** Модели, обученные командой с нуля без сторонних предобученных моделей, разрешены. Платформа переносит только корневые `.py`-файлы и `requirements.txt`; отдельные веса и другие артефакты не копируются. Конкретный способ передачи всех компонентов собственной модели должен соответствовать поддерживаемому формату и правилам; см. раздел 4.5.

## 14. Проверка готовности решения

- В корне ZIP-архива находится `solution.py`; все необходимые собственные импортируемые модули представлены корневыми `.py`-файлами.
- Учтено, что платформа переносит только корневые `.py`-файлы и `requirements.txt`: запуск не зависит от переноса отдельных файлов весов, прочих артефактов или вложенных модулей.
- Если используется заранее обученная собственная модель, она обучена командой с нуля без сторонних предобученных моделей; все необходимые компоненты передаются в поддерживаемом формате с соблюдением правил соревнования.
- Соблюден контракт `baseline.py`, включая окружение, запуск и выходной формат.
- Решение совместимо с Python 3.12 и допустимыми зависимостями.
- Агент, его инструменты и генерируемый код используют только зависимости из `requirements.txt`; в ZIP нет сторонних библиотек и `.whl`.
- При запуске нет обязательного импорта отсутствующего пакета `mcp`; инструменты предоставляет и выполняет скрипт сабмита, а модель выбирает действия и аргументы и получает результаты выполнения.
- Код не обращается к Git и не загружает модули из репозитория во время сабмита.
- Автоматически переданные платформой аргументы обрабатываются по `baseline.py`.
- Каждый запуск работает с материалами одной задачи и не зависит от результатов предыдущей задачи.
- Тип задачи, целевая переменная, метрика и формат предсказаний определяются по материалам текущей задачи.
- Выполняется цикл AutoResearch: гипотеза, эксперимент, оценка на собственной валидации и выбор следующего шага.
- Результаты экспериментов учитываются при выборе лучшего решения.
- Используются только разрешенные данные, модели и LLM-доступ.
- Соблюдены ограничения 8 CPU, 32 GB RAM и 3 часа на задачу.
- `submission.csv` сформирован до истечения времени в каталоге рядом с `solution.py` и `task.md`.
- Промежуточные файлы сохраняются в рабочем каталоге, его подкаталогах или `/tmp`; учтен ориентир 30-35 ГБ свободного места.
- Обработка ограничена текстовыми и табличными данными; изображения, аудио и видео не требуются.
- Один и тот же код решает публичные и ранее неизвестные приватные задачи без ручной адаптации.
- При отправке соблюдается командный лимит 3 сабмитов в день с обновлением в 00:00 по МСК.
- Новая отправка выполняется после отображения score предыдущей; нулевой score также виден в интерфейсе.
