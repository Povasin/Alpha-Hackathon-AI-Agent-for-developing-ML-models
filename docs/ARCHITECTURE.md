# Минимальная архитектура baseline

Статус: структура и ответственность модулей, без реализации. Пять новых Python-файлов содержат только комментарии. Их запуск пока не выполняет пайплайн и не создаёт submission.csv.

Основа — принятая схема Y-v2: [результаты проверки и голосования](reviews/2026-10-20-organizer-docker-scheme-vote/results.md). Требования платформы: [Альфа_Хак_AutoML.md](Альфа_Хак_AutoML.md).

## Структура репозитория

```text
alpha_ML/
├── solution.py          # точка входа и порядок стадий
├── agent.py             # Qwen, действия, исследование, журнал
├── experiments.py       # задача, данные, рецепты, обучение и оценка
├── runtime.py           # время, ресурсы, subprocess, cleanup
├── submission.py        # резерв, проверка CSV, публикация и откат
├── requirement.txt      # существующий фиксированный список зависимостей
├── baseline.py          # существующий образец интерфейса организаторов
├── README.md            # существующая документация репозитория
├── docs/
│   ├── ARCHITECTURE.md  # этот документ
│   ├── Альфа_Хак_AutoML.md
│   └── reviews/         # существующие материалы проверки схемы
└── data/                # существующие локальные данные разработки
```

Добавлено ровно пять `.py` и один документ в существующий `docs/`; новых папок нет. Служебные файлы Git, локальное окружение и секреты в дереве опущены. Отдельные `src/`, `configs/`, `prompts/`, `schemas/`, `tools/`, `models/` и слои абстракций на старте не нужны. Промпты, схемы и настройки поставляются внутри собственных корневых `.py`.

## Ответственность и порядок ручного ревью

| Порядок | Файл | Что проверять |
|---|---|---|
| 1 | solution.py | Старт 10800 секунд до тяжёлых импортов; позиционный путь task.md, default task.md; wiring; ранний резерв; нормальная и аварийная финализация. |
| 2 | runtime.py | Каждый дорогой шаг и retry ограничен общим остатком; один активный опыт; ограничения потоков; таймауты, RAM/диск, остановка потомков. |
| 3 | experiments.py | Точный контракт задачи/метрики; отсутствие утечки; разрешённая грамматика рецептов; реальная генерация и исполнение Python; trainer/evaluator; сопоставимость кандидатов. |
| 4 | agent.py | Единственная LLM — выданный Qwen; проверяемые actions; ограниченные repairs; содержательные гипотезы по фактическим результатам, а не только HPO. |
| 5 | submission.py | Резерв без обучения; готовый CSV до продвижения кандидата; атомарная публикация выбранного финалиста до refit; сохранение результата при сбоях. |

### solution.py

Тонкая точка сборки. Фиксирует t0, настраивает супервизор до загрузки тяжёлых библиотек, обрабатывает аргументы и связывает модули. Последовательно организует чтение задачи, разрешение контракта, ранний резерв, подготовку валидации, исследование и финализацию.

Здесь фиксируются общие развилки: неразрешимая метрика после ограниченного resolver, пустой shortlist, пропуск confirmation/refit, авария до или после первого CSV. Приватные target/метрика не зашиваются. Отдельного orchestration-модуля не требуется.

### runtime.py

Общий срок и исполнение: проверка остатка перед каждым вызовом и после дорогой подготовки, timeout, retries, ограничение потоков, subprocess, наблюдение за памятью/диском/потомками и cleanup. Ограничивает также старт, чтение данных, API, resolver, repair, predict, запись и финализацию.

Получает уже проверенную программу от доверенной ML-части. Возвращает структурированный результат исполнения: статус, код возврата, ограниченный вывод/ошибку, время и ресурсы. Не считает ML-метрику. Watchdog и процесс под тем же UID не объявляются OS sandbox; жёсткая изоляция и права на cgroup не предполагаются.

### experiments.py

Содержит последовательные смысловые разделы внутри одного файла: контракт задачи и данных; протокол валидации; разрешённые операции и компилятор рецептов; trainer/evaluator; подтверждение финалистов и refit. Новые файлы по каждому алгоритму пока не создаются.

TaskSpec определяет тип задачи, target, ID, формат выхода и точную метрику с направлением и параметрами. ValidationSpec хранит неизменный confirmation и версионированный протокол поиска. Сначала отделяется confirmation, затем выполняются target-зависимый профиль и обучение. Все обучаемые преобразования строятся по fit-части. Смена search-split требует сопоставимой переоценки соперников.

Рецепт — проверяемое описание обработки, признаков, модели и параметров. Компилятор создаёт исполняемый Python из разрешённых операторов; trainer управляет fit/predict; evaluator сам вычисляет метрику. Qwen не получает возможность переписывать evaluator, split или принимать своё число из stdout за качество. Неподдержанная метрика проходит конечный resolver без подмены proxy. Это архитектурные требования к будущей реализации, не уже существующие проверки.

### agent.py

Хранит встроенные промпты, описания инструментов и схемы аргументов, адаптер Qwen, разбор ответов и диспетчер разрешённых действий. Поддержка native tools или текстового action-протокола проверяется после получения ключа. Используются точные OPENAI_MODEL, OPENAI_API_KEY, OPENAI_BASE_URL. API-запросы также ограничиваются runtime.

Выбирает draft/debug/improve и новые гипотезы по журналу текущего запуска. Журнал включает parent, рецепт/код, версию валидации, измеренную метрику, статус, ресурсы, ошибки и ссылки на артефакты. Он не управляет исполнением в обход супервизора. Отдельные memory.py, journal.py, llm.py и prompts.py на старте не нужны. Локальный контроллер при сбое API явно отмечается как деградация Qwen-части.

### submission.py

Принимает контракт выхода и предсказания. Форматный резерв создаёт без fit и target-статистик, только если допустимую константу можно определить из контракта/sample. Не обещает поддержку любого private-формата или ненулевой score.

Проверяет CSV, хранит готовые файлы продвинутых кандидатов и резерв, публикует через проверенный temporary на той же файловой системе и атомарную замену. Публикует CSV выбранного финалиста до refit; новый результат refit заменяет его только после успешной проверки. Выбор финалиста по качеству остаётся у доверенной ML-части и управляющей логики. При записи и проверках действует общий супервизор.

## Связи модулей и контракты

solution.py связывает остальные четыре модуля и передаёт зависимости явно. Нижние модули не импортируют solution.py. Runtime остаётся независимым от агента и ML-логики; experiments.py использует его исполнитель; agent.py вызывает разрешённые ML-действия через переданные обработчики. Submission получает контракт/предсказания/пути, а не экземпляр агента. Обратные импорты и циклические зависимости не нужны.

TaskSpec, ValidationSpec, рецепт и результат ML-опыта определяются в experiments.py; состояние бюджета и результат subprocess — в runtime.py; формат action и журнал — в agent.py. Проверка и публикация артефактов принадлежат submission.py. Пока достаточно этих владельцев; отдельного общего types.py не требуется.

Протокол обмена: гипотеза и рецепт → доверенная проверка/компиляция → исполнение через runtime → предсказания и точная метрика → запись фактов в журнал → следующее решение агента. Наличие лучшей метрики ещё не продвигает кандидата: сначала submission.py должен сохранить его проверенный test CSV.

После freeze допускается однократный confirmation фиксированного shortlist при наличии данных и времени. Затем публикуется CSV финалиста и лишь при запасе выполняется необязательный refit. При глобальной аварии новые API/fit/confirmation не запускаются: сохраняется существующий валидный файл и выполняется ограниченный cleanup.

## Архив и файлы одного запуска

В будущий ZIP включаются только пять модулей решения из дерева выше и `requirements.txt` с неизменным содержимым локального `requirement.txt`. Вторую копию списка зависимостей в репозитории сейчас не создаём. При упаковке нужен явный список файлов, а не все корневые `.py`: исходный baseline.py содержит недоступный MCP и в архив решения не входит. README, docs, локальные данные, .env, venv и Git также не поставляются.

При запуске организаторы предоставляют task.md и данные. Во время работы решение сможет создать один служебный каталог `_work/` в папке задачи либо использовать /tmp. Сейчас этот каталог и файлы артефактов не создаются.

```text
<каталог задачи>/
├── solution.py и остальные четыре модуля
├── requirements.txt
├── task.md и входные CSV
├── submission.csv             # опубликованный результат
└── _work/                    # только во время выполнения
    ├── journal.jsonl         # один журнал текущего запуска
    ├── reserve.csv           # сохранённый форматный резерв
    └── trial-<id>.*           # код, результаты и нужные артефакты опытов
```

CSV продвинутых кандидатов сохраняются до завершения выбора; ненужные тяжёлые артефакты очищаются с учётом свободного диска. В следующую задачу память и результаты не переносятся. Итоговый submission.csv находится рядом с solution.py и task.md, не внутри _work.

## Общие границы

- Существующий Docker организаторов: Python 3.12, 8 CPU, 32 GB; GPU, root, собственный образ и nested Docker не требуются.
- Только установленные зависимости из requirement.txt, данные кейса и разрешённый Qwen-канал. Нет обязательного MCP, runtime pip/Git и внешних скачиваний.
- Сторонние pretrained запрещены. Собственные модели с нуля разрешены; базовый путь не зависит от неподтверждённой передачи офлайн-весов.
- Все стадии входят в 10800 секунд. 600 рублей — сутки разработки, не лимит запуска платформы. 30–35 ГБ — ориентир свободного места, не гарантированная квота.
- Отправки и score платформы находятся вне исследовательского цикла. До трёх отправок в день, ожидание предыдущего score, включая ноль.
- Тесты, упаковщик, Dockerfile, новые зависимости и реализация модулей в эту задачу не входят. Проверка импортов/API/отказов и ML-качества выполняется после появления реализации и доступа к целевому окружению.
