# Y-v2: явная исправленная редакция выбранной основы Y

Это новая целая редакция схемы Y после голосования раунда 2 (A/B/C выбрали Y). Она **ещё не ратифицирована**. Исходные `proposal-*.mmd/json`, `candidates.json` и `ballot-*.json` не изменены. Основание правок — blockers и needed_changes всех трёх бюллетеней, актуальное ТЗ, `baseline.py`, `requirement.txt` и 14 границ `protocol.md`. Новая схема не является произвольным объединением X/Y/Z.

В рамках этой редакции выполнен статический разбор. Docker организаторов, API Qwen, ML-обучение и установки пакетов не запускались. Ни импортная совместимость, ни native tool calling, ни качество модели не объявляются проверенными. Целевой образ и ключ пока не предоставлены.

## Управляющие правила схемы

1. Все узлы с пометкой **«Шаг»** выполняются только через обязательный вызов супервизора: `supervisor.step(operation, remaining_budget)`. Это семантика каждого такого узла, а не необязательная рекомендация одного стартового узла. Она распространяется также на вложенные операции: API-запросы и их retries, resolver, repair, импорт, чтение/профиль, компиляцию, fit/predict, evaluator, запись/restore/replace, confirmation и cleanup. Перед каждым новым вызовом и после дорогой подготовки повторно проверяется остаток, а его timeout ограничивается оставшимся общим временем с резервом на сохранение уже готового результата и остановку потомков. Один активный опыт упрощает контроль совокупных 8 CPU/32 GB.
2. Супервизор устанавливается с `t0` в начале `solution.py`, до тяжёлых импортов; весь срок составляет 10800 секунд. Мягкий дедлайн поиска предшествует общему пределу. Нормальный отказ gate `B` замораживает поиск. Глобальная авария/мягкая остановка не начинает дорогие confirmation/refit: `ERR` прекращает активную работу, сохраняет проверенный CSV и допускает только bounded cleanup. Завершение процесса после 10800 секунд не считается допустимым планом финализации.
3. Сплошные стрелки задают порядок работы. Две пунктирные стрелки задают только глобальное применение супервизора и его аварийное прерывание: **пунктирной feedback-дуги в планировщик нет**. `LOG` обновляет состояние и результат инструмента; новый вызов планировщика осуществляется через `BETTER -> B` либо `PROMOTE -> B`. Перед `TEST` и всеми последующими шагами действует тот же обязательный wrapper. Чтение истории моделью происходит в защищённом вызове `PLAN`, а не при записи журнала.
4. Ограниченные retries живут внутри `supervisor.step`, каждая попытка снова проверяет ресурсы. После исчерпания retries или неожиданной ошибки любого шага вызывается `ERR`. До первого валидного CSV это `FAIL` с bounded cleanup; после первой публикации — сохранение последнего проверенного CSV и `CLEAN`. Ошибка первой записи не допускает продолжения в `SPLIT`. Ожидаемые ошибки исследовательского кода могут вместо глобального прекращения стать отрицательным результатом `LOG`; незавершённый/невалидный опыт не продвигается. Ошибка cleanup не удаляет CSV и не запускает бесконечную рекурсию handler: завершается best-effort остановка в оставшемся бюджете. Абсолютную остановку каждого потомка без cgroup/привилегий схема не гарантирует.

## Что исправлено относительно исходной Y

- Добавлен `RESOLVE` с раздельным назначением вызова (выходной контракт либо точная метрика/адаптер), конечным числом попыток и общим временем. Он сверяет `task.md`, фактический dictionary, train/test/schema и sample; успешный результат возвращается соответственно к `C` или `M`. Само имя незнакомой метрики больше не означает немедленный отказ. Реализуемая точная формула может собираться только из проверяемых операторов доверенного реестра, с проверкой направления, параметров, labels/shape и контрольных примеров; произвольный Python-evaluator от Qwen и число из stdout не принимаются. Если проверить точное значение невозможно, proxy не используется. Resolver локальный; уже проверенный Qwen может помогать интерпретации только через тот же gate и без получения запрещённых данных.
- Исчерпание resolver контракта без валидного выхода означает `FAIL`. Исчерпание resolver метрики означает `FINAL -> CLEAN` с уже созданным форматным резервом, без selection-by-quality, confirmation и refit. Счётчики resolver и его цель сохраняются в состоянии; повторная неуспешная проверка `C/M` не обнуляет лимиты.
- Дедлайн, ресурсы и повторные действия больше не могут обходиться прямой дугой журнала в планировщик. Ошибки, retries и глобальная финализация заданы отдельным правилом. На самой границе времени запрещено начинать новый дорогой confirmation.
- API использует буквальные `OPENAI_MODEL`, `OPENAI_API_KEY`, `OPENAI_BASE_URL` из `baseline.py` и §13.3 ТЗ. Доступная разрешённая LLM — Qwen3.8-27B; фактический model ID и endpoint сверяются после доступа. `API` передаёт имена, описания и схемы аргументов инструментов; `MODE` фиксирует поддержанный native tools либо строго разбираемый текстовый action-протокол. JSON/native tools не выводятся из самого факта наличия списка actions. Модель выбирает action/arguments, скрипт валидирует и исполняет, `LOG` сохраняет фактический ответ для следующего защищённого вызова модели.
- При отсутствии проверенного API выбирается явный режим local controller. Он может адаптировать разрешённые гипотезы по исполненным опытам без другой LLM, но это **деградация**, а не подтверждение полноценной Qwen-части. Режим хранится в состоянии: неработающий API не вызывается заново на каждой итерации без разрешённой ограниченной повторной проверки через супервизор.
- Ранний резерв остался константным: без fit, target-статистик train и подглядывания в будущий confirmation-target. Константа определяется только поддержанным контрактом/примером допустимого выхода, а не средним/модой labels. Если допустимую константу нельзя построить/проверить, resolver исчерпывается честным отказом; универсальный резерв для любого контракта не обещается. После публикации `SPLIT` сначала фиксирует confirmation, затем строит search-split и target-зависимый профиль только на fit-части. При отсутствии возможности выделить confirmation это явно отмечается, независимое подтверждение впоследствии не заявляется.
- При гипотезе смены search-validation сохраняется неизменным confirmation. Новая версия протокола требует переоценить сравниваемые рецепты на общем split в том же бюджете; несопоставимые score не используются для продвижения.
- `FREEZE` явно проверяет наличие законченных оценённых кандидатов с готовыми CSV. Пустой shortlist оставляет резерв и сразу завершает работу без confirmation/refit. Правила shortlist, пороги, ансамблевые веса и рецепты замораживаются до confirmation. Сам резерв не выдаётся за оценённого финалиста.
- `CONFQ` — явная условная ветка: confirmation выполняется один раз только при заранее отделённых данных и времени на **всю** процедуру с последующими публикацией и cleanup. Иначе выбор идёт по search-validation с оговоркой о переоптимизации, а не с вымышленной независимостью.
- `SELECT` теперь выбирает, проверяет и **атомарно публикует CSV именно выбранного финалиста до refit**, сохраняет копию. No-refit ветка использует этот файл. `REFITQ` требует существующий выбранный обучаемый рецепт и достаточный остаток. Сбой refit оставляет опубликованный CSV финалиста; сбой самой публикации финалиста сохраняет последний ранее валидный CSV. Результат refit оценивается на тех же labels не как новая независимая оценка.
- Запись первого резерва, продвижение, восстановление финалиста и refit используют проверенный temporary-файл на той же файловой системе и atomic replace. Проверка готовности файла precedes продвижение. Для каждого продвинутого кандидата хранится отдельный CSV. Последующий отказ диска/replace/cleanup не удаляет последний валидный `submission.csv` и резерв.

## Остальные условия ТЗ и честные ограничения

`SPEC` читает `task.md`, `train.csv`, `test.csv`, `data_dictionary.csv`, `sample_submission.csv` по текущим путям. Первый позиционный аргумент — путь описания, без него `task.md`; рабочая папка — папка задачи, итоговый `submission.csv` рядом с `solution.py/task.md`. Наличие служебного режима MCP из baseline не является обязательством его воспроизводить. CSV — UTF-8, запятая, десятичная точка, пустая ячейка как missing. Фактический dictionary читается по именам полей; `unit` для классификации не предполагается. Обработка ограничена текстом и таблицами, изображения/аудио/видео не требуются. Новые неизменяемые до отправки адаптеры используют только установленные пакеты; неизвестный произвольный private-контракт не объявляется гарантированно поддержанным.

На public регрессия оптимизирует RMSE вниз, классификация Macro F1 вверх; Accuracy/Weighted F1 остаются справочными. Точные labels/zero_division Macro F1 требуют проверки. `S_reg=100*max(0,1-RMSE/B_RMSE)`, `S_cls=100*max(0,(MacroF1-B_F1)/(1-B_F1))`, среднее двух public/private баллов — внешние правила платформы. Неизвестные B_RMSE/B_F1 и скрытые labels нельзя выдумывать для локального score. На private точная метрика определяется заново; нормировка не служит oracle внутри запуска.

Грамматику рецептов и доверенный evaluator предстоит реализовать и проверить. Она должна поддерживать содержательные новые комбинации признаков/предобработки/моделей, а не маскировать фиксированный HPO. Свобода произвольных Python-патчей сознательно ограничена, поскольку доступная среда не подтверждает sandbox для них. Любые числа резерва времени, folds, потоков, RAM-запаса и retry-пределов — параметры для измерения, не доказанный оптимум.

После доступа к среде отдельно нужны smoke-проверки реального переноса, импортов/ABI на Python 3.12, argv/env/output, разрешённого Qwen-протокола и квот, раннего CSV, границ timeout/OOM, записи/rollback и cleanup в общем дедлайне. Эта редакция описывает такие требования, а не выдаёт их за выполненные тесты. Все действия Ozon по постоянному правилу пользователя остаются только чтением; эта архитектурная работа Ozon не затрагивает.
