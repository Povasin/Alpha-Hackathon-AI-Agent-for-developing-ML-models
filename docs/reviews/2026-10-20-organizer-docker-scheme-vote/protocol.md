# Независимая перепроверка схемы в Docker организаторов

Дата: 20 октября 2026 года. Цель — выбрать одну полную схему, а не произвольно смешать лучшие фрагменты разных вариантов. Это статическая архитектурная оценка: образ организаторов и ключ Qwen не предоставлены, фактический запуск в целевом Docker не подтверждён.

## Источники

- Актуальный `docs/Альфа_Хак_AutoML.md`, прочитать полностью, включая новые §§3.1, 4.4, 4.5 и checklist §14.
- Корневой `requirement.txt`: перечень установлен в Docker организаторов, согласно уточнению пользователя. В контракте переноса называется `requirements.txt`; локальный источник не переименовывать и не менять его состав.
- `baseline.py`: контракт argv/env/вывода, а не разрешение зависеть от отсутствующего MCP.
- `prior-scheme.mmd`: схема из предыдущего ответа, подлежащая перепроверке.

## Обязательные границы

1. Организатор запускает ZIP-решение в своём Docker, Python 3.12, 8 CPU, 32 GB RAM; собственный образ, nested Docker, привилегии, cgroup write access и GPU не предполагаются.
2. В контейнер переносятся только корневые `.py`-файлы и `requirements.txt`. Собственные промпты, схемы и конфигурация должны быть доступны из переносимого кода, без обязательных внешних JSON/YAML/Markdown, вложенных модулей и отдельных весов. Создание рабочих файлов во время запуска разрешено.
3. Отсчёт 10800 секунд начинается с запуска кода. Импорты, LLM/API, профилирование, fit/predict, запись, проверки и остановка процессов входят в срок.
4. Используются только перечисленные зависимости. MCP отсутствует, baseline нельзя запускать без адаптации; инструменты описывает, проверяет и исполняет сам скрипт. Модель возвращает действие/аргументы, получает результат и выбирает следующий шаг.
5. Qwen 3.8 — разрешённая LLM, ключ пока не выдан. Endpoint, model ID, поддержка tools/JSON и квоты проверяются после доступа. Нельзя считать выбор actions эквивалентом доказанной поддержки native tool calling.
6. Нет общего интернета, Git, pip, внешних данных или скачивания моделей в runtime; предусмотренный платформой Qwen-канал — исключение. 600 рублей — бюджет суток разработки, не запуска. Квоты API не объявлять бесконечными.
7. Сторонние pretrained запрещены; собственные модели, обученные с нуля, разрешены при соблюдении данных/формата переноса. Способ передачи заранее подготовленных весов не подтверждён, отдельные файлы не копируются; схема не должна зависеть от них. Не вводить абсолютный запрет на все собственные модели.
8. Один неизменяемый код работает на public и новых private задачах; нет межзадачного состояния и промежуточного feedback платформы. Цель/метрика/формат определяются из текущих материалов, неизвестная метрика не подменяется proxy.
9. AIDE-подобный AutoResearch выбирает содержательные гипотезы по исполненным опытам; доверенный recipe/trainer/evaluator контролирует fit/predict и score, а не принимает число из stdout. Код действительно генерируется и исполняется; это не только фиксированный HPO.
10. Процесс, отдельный cwd, AST и очищенный env не являются OS sandbox. Нельзя обещать защиту доверенных данных при произвольном Python под тем же UID; cgroup только при наличии возможностей, иначе мониторинг best effort.
11. До kill должен существовать валидный submission.csv рядом с solution.py/task.md. Нужны ранний резерв, хранение CSV каждого продвигаемого кандидата, атомарная публикация и откат при ошибках/timeout/refit. Форматный резерв не гарантирует score или поддержку любого контракта.
12. В рабочем каталоге/подкаталогах и /tmp можно создавать файлы; 30–35 ГБ — ориентир свободного места, не квота.
13. Confirmation при наличии данных/времени — однократно после заморозки shortlist, до финального выбора не используется для обучения/адаптивного поиска. Final refit необязателен и зависит от бюджета; после него независимая оценка на тех же labels не заявляется.
14. Правила отправок — внешняя процедура разработки: максимум 3 в день, ждать score предыдущей, включая нулевой. Агент не получает этот score внутри своего исследовательского цикла.

## Процедура

- Раунд 1: три автора с раздельным контекстом не читают чужие предложения до фиксации своих. Каждый создаёт полную схему Mermaid и аудит соответствия актуальному ТЗ.
- Тексты и исходные файлы фиксируются хешами. Модератор составляет обезличенный набор X/Y/Z; варианты схем не редактируются.
- Раунд 2: каждый независимо выбирает лучший полный вариант, ранжирует остальные и указывает реальные дефекты/непроверенные предположения. Можно голосовать за любой вариант, включая совпавший со своим; это обезличивание, не гарантия полного ослепления.
- Победитель — минимум 2 из 3 голосов. При 1–1–1 — повторный разбор и голосование. Нарушение обязательного условия не перекрывается числом голосов: схема исправляется явно и переголосовывается.
- Выбранная схема проходит финальную проверку соответствия всех источников и отсутствия незамкнутых критических веток. Результат в ответе совпадает с зафиксированной победившей Mermaid-схемой.
- Обязательные параметры отличаются от предварительных настроек. Доли времени, 20% holdout, шесть потоков, около 24 GB и repair/retry-пределы не объявляются измеренными оптимумами.
