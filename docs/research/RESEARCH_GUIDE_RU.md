# Альфа Хак: как подготовиться к универсальному ML-агенту за 7 дней

Дата исследования: **20 октября 2026 года**. Профиль участника: уже умеет строить ML-модели; LLM-агенты — новая область. Это исследовательская подготовка: решение для сдачи не реализовано, модели не обучались, внешний LLM API не вызывался.

**Главный вывод:** твой основной пробел сейчас — управление автономными экспериментами. Приоритет: понять цикл «LLM → инструмент → реальный результат → следующая гипотеза», затем совместить его с привычным табличным ML. Наиболее близкие открытые аналоги — AIDE, MLE-bench, R&D-Agent и MLE-STAR. Для публичной регрессии есть материалы WiDS 2022, для классификации — UNSW-NB15.

## 1. Что именно нужно выиграть

По локальной [постановке](../Альфа_Хак_AutoML.md) результат — один ZIP с `solution.py`, который получает описание **ранее неизвестной** задачи и данные, проводит эксперименты и сохраняет предсказания. Публичные датасеты — проверка разработки; итог определяют две скрытые задачи. Их типы и метрики заранее не раскрыты.

Ограничения из постановки: Python 3.12, 8 CPU, 32 GB RAM, максимум 3 часа **на задачу**, контейнер без общего интернета; только предоставленные данные и разрешённые зависимости; предобученные ML-модели запрещены. Разрешённая LLM предоставляется отдельно через API. В документе она обозначена `Qwen3.8-27B`; точный идентификатор и endpoint нужно получить у организаторов. 600 рублей — эквивалент дневного командного лимита при разработке, а не установленный бюджет каждого запуска. Сабмитов — 3 в день.

Публичный score — среднее двух нормированных оценок:

```text
S_reg = 100 × max(0, 1 − RMSE / B_RMSE)
S_cls = 100 × max(0, (MacroF1 − B_F1) / (1 − B_F1))
Score_public = (S_reg + S_cls) / 2
```

Числа B_RMSE и B_F1 в материалах отсутствуют. Выше порога положительной оценки уменьшение RMSE на Δ даёт прирост public score `50×Δ/B_RMSE`, а увеличение Macro F1 на δ — `50×δ/(1−B_F1)`. Поэтому сравнивать пользу часа работы по сырым величинам двух метрик нельзя. Это вывод из формул, а не измеренный результат.

Для победы важны три независимых свойства: сильное ML-решение, правильный выбор экспериментов и гарантированное появление корректного CSV до дедлайна. Моё предположение о наиболее перспективном направлении: **надёжный ML-исполнитель + LLM, выбирающая содержательные гипотезы + неизменяемая процедура оценки**. Преимущество этого подхода на вашем лидерборде ещё предстоит проверить.

Для временной задачи нельзя механически применять GroupKFold по годам, если он обучает на будущем ради предсказания прошлого. Основы выбора split разобраны в [документации scikit-learn 1.5](https://scikit-learn.org/1.5/modules/cross_validation.html).

Это оценка годового EUI при уже известных погодных показателях года. Не нужно автоматически превращать её в прогноз почасового спроса на энергию. Первая оценка: стратифицированное разбиение с отчётом F1 каждого класса; дополнительная — разбиение с удержанием групп одинаковых признаков целиком. Эти протоколы отвечают на разные вопросы. Групповая проверка — стресс-тест обобщения, а не доказанно точная копия официального test. Выбирай кандидатов на фиксированном основном протоколе; не сравнивай метрики разных splits как одну шкалу.

При 20%-й валидации ожидается около 13 примеров Worms. Изменение нескольких ответов заметно меняет F1 класса и Macro F1. Стабильность важнее сотых долей улучшения на одном случайном seed.

## 3. Агентная часть с нуля — на языке ML-инженера

**LLM** предлагает следующий эксперимент и может написать код. **Инструмент** — Python-функция, которую исполняет твоя программа по запросу LLM. **Оркестратор** управляет вызовами, состоянием, временем и сохранением артефактов. **Память экспериментов** — записи о реально выполненных попытках. **Оценщик** вычисляет метрику по сохранённым предсказаниям на фиксированном split.

Пример цикла: агент видит низкий recall Worms → предлагает умеренные веса классов → исполнитель обучает модель → оценщик возвращает Macro F1, precision/recall классов и время → агент решает сохранить изменение или вернуться к предыдущей версии. Метрика из исполнения, а не уверенный текст LLM, определяет результат.

Полезные понятия для первого дня:

| Понятие | Как оно проявляется в вашем кейсе |
|---|---|
| Tool calling | Модель возвращает имя функции и аргументы; код приложения выполняет функцию |
| Observation | Реальные `stdout`, `stderr`, код завершения, JSON с метриками |
| State | Тип задачи, таргет, metric direction, split ID, лучший результат, оставшееся время |
| Context | Часть истории, отправленная модели; файлы на диске сами в неё не попадают |
| Repair loop | Ограниченное число попыток исправить ошибку с показом traceback |
| Research loop | Новая ML-гипотеза после успешного запуска предыдущего эксперимента |
| Checkpoint | Сохранённый лучший код, модель, конфигурация и валидный submission |
| Workflow | Фиксированные технические стадии: загрузка, проверка, исполнение, оценка |
| Agent | Выбирает следующую содержательную гипотезу с учётом обратной связи |

Начни с [Hugging Face: What is an Agent?](https://huggingface.co/learn/agents-course/en/unit1/what-are-agents), [Tools](https://huggingface.co/learn/agents-course/en/unit1/tools) и [цикла Thought–Action–Observation](https://huggingface.co/learn/agents-course/en/unit1/agent-steps-and-structure). Для задачи достаточно понимать смысл и интерфейс цикла; длинное текстовое рассуждение модели само по себе не является экспериментом.

Моя рекомендация при семи днях и отсутствии опыта с агентами: один исследовательский агент и обычный Python-оркестратор. Разные роли при необходимости можно выразить разными запросами к той же разрешённой модели. Увеличение числа агентов полезно только после измерения пользы относительно токенов, времени и сбоев. Простые составные схемы и различие workflow/agent хорошо объясняет [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).

Гипотезы, которые имеют смысл проверить позже: CatBoost/LightGBM без сложной подготовки; индикатор отсутствия ENERGY STAR; импутация рейтинга, обученная только на train-fold; взаимодействия назначения, площади и погоды; проверка сырого таргета против log-target по **исходной RMSE**; ансамбль только при устойчивом выигрыше. `exp(E[log(y)|x])` не равно `E[y|x]`, поэтому логарифмирование таргета не является бесплатным улучшением RMSE. ### UNSW-NB15 — читать критичнее, чем рекламные цифры

1. **[Официальное описание UNSW](https://research.unsw.edu.au/projects/unsw-nb15-dataset)**. Источник смысла признаков, происхождения и официальных splits. Полезнее для постановки, чем случайная статья с «99% accuracy».
2. **[UNSW-NB15 EDA — Md Khairul Islam](https://www.kaggle.com/code/khairulislam/unsw-nb15-eda)**. Страница ноутбука подтверждена; содержимое всех ячеек не аудировано. Использовать как дополнительный разбор трафиковых признаков.
3. **[Kaggle writeup: Binary & Multi-Class Network Attack Classification, 2026](https://www.kaggle.com/competitions/advanced-ai-for-cybersecurity-intrusion-detection-with-unsw-nb-15/writeups/new-writeup-1776760930392)**. Автор описывает отдельные XGBoost-ноутбуки для бинарной и десятиклассовой задач. Полезен для сравнения постановок; это другой учебный хакатон, не доказанное победное решение Альфы.
4. **[simgsr/kaggle_ai_cybersecurity](https://github.com/simgsr/kaggle_ai_cybersecurity)**. В README есть каскад normal/attack → тип атаки, признаки отношений и настройка решений по вероятностям. Число F1≈0.93 относится к **бинарной** задаче; оно не является вашей Macro F1. `skops` не указан в разрешённых зависимостях. Код и качество не воспроизводились.

Не включён в основной список `ihmorol/unsw-nb15-handling-binary-multiclass-ids`: поисковый индекс описывает полезный проект, но прямое открытие дало 404. Не рекомендую тратить на него время до проверки доступности. У другого найденного `nakul-cloud` README перечисляет 9 классов и пропускает Shellcode: такой ресурс требует аудита перед переносом, поэтому он не опорный.

Перспективные гипотезы для ваших данных: веса классов; умеренный подбор параметров бустинга; ratios source/destination; выделение ошибок Analysis/Backdoor/DoS; подбор правила выбора класса по OOF-вероятностям; сравнение простой мультиклассовой модели и каскада. Каскад может терять атаки на первом этапе. Веса редких классов могут увеличить false positives. Подбирать всё следует на train-only валидации.

SMOTE после случайного числового кодирования протоколов способен создавать бессмысленные промежуточные категории. Если он нужен, рассматривать подход для смешанных признаков и применять resampling **только внутри train-fold**. Утечку при resampling подробно показывает [официальная документация imbalanced-learn](https://imbalanced-learn.org/stable/common_pitfalls.html). Для CatBoost проверять определение `TotalF1` и `use_weights`, а итоговую соревновательную метрику пересчитывать единым независимым оценщиком: [официальные multiclass metrics](https://catboost.ai/docs/en/concepts/loss-functions-multiclassification).

## 7. Какие AutoML-библиотеки реально полезны

Фактический файл в проекте называется **`requirement.txt`**. В нём разрешены CatBoost 1.2.8, LightGBM 4.6.0, XGBoost 2.1.4, scikit-learn 1.5.2, Optuna 4.2.1, AutoGluon Tabular 1.3.1, LightAutoML 0.4.2 и FLAML 2.3.6. Наличие строки не подтверждает работоспособность всех транзитивных зависимостей в образе.

| Инструмент | Роль в возможном решении | Что изучить |
|---|---|---|
| CatBoost / LightGBM | Быстрый рабочий результат, дешёвые эксперименты, контроль CPU | Время обучения, категории, missing, early stopping |
| [AutoGluon 1.3.1](https://auto.gluon.ai/1.3.1/tutorials/tabular/tabular-essentials.html) | Сильный автоматизированный кандидат и ансамбли | `eval_metric`, `time_limit`, явная валидация, bagging/stacking, доступные модели |
| [FLAML](https://github.com/microsoft/FLAML) | Экономный выбор модели и гиперпараметров | Бюджет, доступные estimators, splits, метрика |
| [LightAutoML](https://github.com/sb-ai-lab/LightAutoML) | Альтернативный табличный backend | Ресурсные ограничения, категория задачи, CPU-параллелизм |
| Optuna | Точечный тюнинг удачного семейства | Ограничение времени, pruning, фиксированная схема оценки |

Запускать все AutoML-системы одновременно на 8 CPU — непроверенная и рискованная стратегия: каждая может занять все потоки. Начни с последовательных измерений. `time_limit` библиотеки не заменяет внешний дедлайн, запас на предсказание и проверку файла. Не использовать автоматически современные пресеты с предобученными foundation models: запрет кейса сохраняется и при наличии такого пресета в новой документации.

Важно: простой неизменный вызов AutoGluon ещё не покрывает заявленное требование AutoResearch. Агенту нужны проверяемые решения по результатам: сменить представление данных, уточнить гипотезу, отвергнуть изменение или перераспределить бюджет.

## 8. Разбор вашего baseline.py

Этот файл уже показывает простейшего агента, полезного для обучения:

1. Читает task.md и имя модели из `OPENAI_MODEL`.
2. Поднимает MCP-сервер с инструментом `run_python(code)`.
3. Передаёт LLM описание инструмента.
4. Получает вызов, исполняет Python, возвращает текст результата модели.
5. Повторяет цикл до завершения или 100 шагов.

Новый процесс при каждом вызове не сохраняет Python-переменные. Файлы сохраняются. Это объясняет, зачем явно записывать конфигурации, результаты и модели на диск. MCP здесь — способ подключения инструмента; для понимания агентного цикла сначала достаточно проследить вызов и ответ.

Пробелы, видимые при чтении, до исправлений:

- Инструкция просит «самую простую» модель; нет оформленного журнала гипотез, политики улучшения и независимого сравнения.
- Есть timeout 1 800 секунд одного `run_python`, но нет общего watchdog на 3 часа или гарантии раннего submission.
- Сохраняются последние 12 000 символов stdout/stderr, но в историю могут накапливаться 100 ответов. Нужны компактные структурированные результаты и сводка.
- Отсутствие `tool_calls` сразу завершает работу; существование и корректность CSV отдельно не проверяются.
- Инструмент передаёт дочернему процессу сильно сокращённое окружение; настройки ресурсов и перенос окружения нужно продумать явно.
- В `requirement.txt` нет явной строки `mcp`, хотя baseline его импортирует. Это вопрос к фактическому Docker-образу, а не доказанный runtime-сбой.
- В обоих task.md прописаны пути `regression/participants/...` и `multiclass/participants/...`, которые **не соответствуют локальному расположению CSV**. Агент должен определять реальные пути из разрешённого каталога, а не слепо исполнять текстовые пути.
- В классификационном `data_dictionary.csv` поле `unit` фактически есть; сомнение общего описания разрешено локальной проверкой.

Baseline не запускался, ключ не запрашивался. Наличие импортов и несовпадение путей проверены статически; совместимость и контракт платформы нужно проверить отдельно.

## 9. Архитектура, которую стоит понимать перед кодингом

Это предложение для будущей реализации, не готовый код.

```text
Материалы задачи → проверенный TaskSpec → профиль данных → выбор split
  → ранняя рабочая модель и submission
  → LLM предлагает одну гипотезу
  → ограниченный исполнитель запускает эксперимент
  → независимый оценщик считает метрику и проверяет артефакты
  → журнал + обновление лучшего решения / откат
  → повтор, пока есть ресурс → финальное обучение → проверенный CSV
```

LLM должна видеть тип задачи, ключевые особенности данных, результаты лучших и неудачных попыток и остаток бюджета. Не отправляй ей весь CSV или длинную историю без отбора. Формат гипотезы: «что меняю; почему это может помочь; как проверю; сколько времени потрачу; когда отвергну».

Оценщик сохраняет фиксированные индексы split и список классов, считает метрики из фактических предсказаний и не разрешает эксперименту менять саму процедуру оценивания. Журнал хранит `experiment_id`, `parent_id`, гипотезу, конфигурацию/код, split ID, метрику, seed, время, ошибку и пути артефактов. После изменения split прежние цифры хранятся отдельно.

Рабочая стартовая раскладка 180 минут: до 15 минут — профиль, split и валидный первый CSV; до 105 — дешёвые гипотезы; 105–140 — подтверждение лучших и возможный ансамбль; 140–165 — финальное обучение; 165–180 — предсказания, проверки, запас. Это ориентир: точные доли определят замеры на 8 CPU. Дедлайн должен учитывать уже потраченное время, а не начинаться заново после ошибки.

## 12. Границы достоверности

**Проверено:** локальные условия, код baseline, список зависимостей, структура и агрегаты CSV; страницы первичных исследований и репозиториев; страницы/описания учебных видео и Kaggle-материалов. **Не проверено исполнением:** качество чужих решений, ваш ML-score, работа LLM endpoint, Docker-образ и воспроизведение видео. Для Kaggle часть содержимого известна только из поискового индекса; непрочитанные ячейки не выдаются за аудированный код.

**Рекомендации:** архитектура, приоритеты, splits и расписание — выводы из ограничений и анализа, которые нужно подтвердить экспериментами. Даже сильный открытый агент не гарантирует победу на иных скрытых данных и с другой LLM.

Оформление HTML-версии использует резервный вариант Lavish: Tailwind/DaisyUI, поскольку в проекте нет собственной дизайн-системы. Полный Markdown остаётся локальным текстовым источником и читается без интернета. Поиск и фильтры HTML работают локально; оформление через CDN требует доступа к сети.
